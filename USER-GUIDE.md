# House: руководство пользователя

House это общий канал между окнами omp в одном проекте. Окна могут работать на
разных профилях; код дома от профиля не зависит. Это руководство описывает
установку, первый запуск, ежедневную работу и восстановление.

Краткое описание архитектуры и команды есть в [`README.md`](README.md).

Платформа: House разработан и проверен только на Windows 10 и 11. Установщик,
`house-init.cmd` и замер времени старта процесса используют cmd и PowerShell.
Ветка `/proc` для Linux в коде есть, но не тестировалась.

## 1. Что устанавливается и как часто

Установка нужна **один раз** в каждом профиле omp, который будет участвовать в
домах. Повторять её перед каждым запуском не нужно.

```powershell
cd <путь к репозиторию House>
node install.mjs --profile <profile-a>
node install.mjs --profile <profile-b>
```

Проверка без изменений:

```powershell
node install.mjs --profile <profile-a> --dry-run
```

Повторная установка нужна только когда:

- подключается новый профиль;
- в репозитории вышла новая версия House;
- `verify` показывает расхождение профиля с источником.

После установки или обновления нужны новые окна omp этого профиля: расширения и
хуки читаются при старте сессии.

Установщик копирует файлы в `<USERPROFILE>\.omp\profiles\<profile>\agent\`, делает
бэкапы, сверяет md5 и пишет манифест `house-install.json`.

## 2. Модель дома

Дом это каталог `.house` в проекте:

```text
<проект>\.house\
```

В нём лежат:

- `house.json`: роли, участники, профили, sessionId, режимы;
- `sessions.json`: живые сессии, PID и время старта;
- `state.json`: метки отправки и доставки;
- `переписка.md`: общий журнал блоков;
- `logs\courier.log`: решения курьера;
- `logs\inbox.log`: фактическая доставка в окна.

Один каталог `.house` это один канал. Чтобы агенты видели общую переписку, они
должны найти один и тот же `house.json`.

Дом ищется в текущем каталоге и вверх по родителям. Поэтому окно можно запускать в
подкаталоге проекта, но не в соседнем каталоге, который не является дочерним.

## 3. Первый запуск нового проекта

### 3.1. Инициализация

```powershell
cd C:\work\my-project
node <путь к репозиторию House>\src\house.mjs init --scope project
```

`init` создаёт `.house`, `house.json`, пустые `sessions.json` и `state.json`,
`переписка.md`, `installed.json` и запускалку `house.mjs`.

Роли на этом шаге необязательны: они выбираются или вводятся в `/house setup`.
Если роли уже известны:

```powershell
node <путь к репозиторию House>\src\house.mjs init --scope project --roles architect,executor
```

Копия `house-init.cmd` в проекте берёт первым аргументом имя установленного профиля,
вторым необязательный список ролей:

```powershell
.\house-init.cmd <profile-a>
```

Пустой ответ на вопрос о ролях означает выбор в `/house setup`.

### 3.2. Запуск окон

Открой два окна в проектном дереве дома:

```powershell
omp --profile <profile-a> --cwd C:\work\my-project
omp --profile <profile-b> --cwd C:\work\my-project
```

`--cwd` не обязателен, если перед `omp` сделан `cd` в тот же каталог. Запуск из
другой папки без `--cwd` даёт сессию с неверным рабочим каталогом: агент может не
найти дом или найти чужой.

### 3.3. Привязка ролей

В одной из сессий выполни `/house setup` **один раз** и выбери в общем списке все
нужные сессии. Не запускай setup отдельно в каждом окне: команда сохраняет привязки
для всего дома.

Список показывает только сессии текущего каталога. Строка выглядит так:

```text
№2 · 01a2054d · 22:08 · ARCHITECT: ревизия API  ← это окно
```

Номер, короткий id, время старта и заголовок сессии. Строка текущего окна помечена
`← это окно`; номер можно проверить из любого окна командой `/house whoami`.
Сессия из другого каталога видна через `/house setup --all`.

Для каждой выбранной сессии задаётся роль: готовая из `house.json` или своя,
введённая текстом. Опечатка проверяется по расстоянию до известных ролей. Имя сессии
по умолчанию совпадает с ролью, своё задаётся отдельно:

```text
/house rename Executor исполнитель
```

Setup передаёт `bind` флаг `--allow-other-session`, потому что привязывает чужие окна
из процесса текущего окна. Ручной CLI `bind` без флага привязывает только своё окно:
`PI_SESSION_ID` процесса должен совпасть с `--session-id`, иначе команда вернёт
`SESSION_MISMATCH` и `house.json` не изменит.

Повторный `bind` заменяет привязку роли, а не добавляет вторую. Живые дубли одной
роли схлопываются: House сохраняет `participantId` из `state.lastSentBy` (а без
метки id существующей привязки) и прежнее имя, если новый `bind` не передал своё.
Две разные роли на одной сессии остаются двумя привязками. Если у роли был мёртвый
дубль с именем, имя переезжает на живую запись.

После привязки запусти курьер и проверь статус:

```text
/house start
/house status
```

Статус показывает имя, роль, профиль, короткий sessionId и состояние привязки. Если
команда `/house` неизвестна, профиль не загрузил расширение: проверь установку и
перезапусти omp.

После обновления House закрой и открой окна заново, иначе в них останется старый код.

Если окна открыты раньше дома, перезапускать их не нужно: поллер находит дом в
течение десяти секунд после создания и доставляет накопленное первым тиком.

### 3.4. Обмен сообщениями

Отправка выполняется командой, а не обычным текстом в чат. Первый аргумент это роль
отправителя в текущей сессии, не получателя:

```text
/house say architect Проверка связи
/house say executor Ответ от executor
/house say architect --to executor "Готовлю схему ответа, посмотри после правки"
```

Адресат задаётся флагом `--to`, роли через запятую. Без флага блок видят все роли.
Адресный блок получают только перечисленные роли: курьер будит их, окна остальных
блок не доставляют, напоминание его не считает. Файл переписки остаётся общим:
адресация управляет доставкой, а не чтением.

Обычный текст в окне агента остаётся сообщением этому агенту и в журнал не попадает.

Правило по умолчанию: **молчание**. Блок пишется, только если коллеге есть дело:
вопрос, просьба, решение, меняющее его работу. Подтверждения, согласия,
благодарности и «принято» не пишутся: каждый блок будит чужое окно и возвращает
ответ. Та же норма в тексте инъекции: отвечай, только если спросили.

Механический предохранитель от затянувшейся цепочки это `courier.autoTurnLimit`,
см. §12.

## 4. Разные профили в одном корне

Это основной и рекомендуемый вариант:

```text
C:\work\my-project\
├── .house\
├── src\
├── package.json
└── ...
```

```powershell
omp --profile <profile-a> --cwd C:\work\my-project
omp --profile <profile-b> --cwd C:\work\my-project
```

Профиль определяет код и настройки агента, `.house` определяет общий канал проекта.
Разные профили не мешают друг другу.

## 5. Один агент в корне, второй в подкаталоге

```text
C:\work\my-project\
├── .house\
├── backend\
└── frontend\
```

```powershell
omp --profile <profile-a> --cwd C:\work\my-project
omp --profile <profile-b> --cwd C:\work\my-project\frontend
```

House ищется вверх по каталогам, поэтому сессия из `frontend` найдёт
`C:\work\my-project\.house`. Правило: рабочий каталог окна должен быть в том же
дереве, что и дом.

## 6. Git worktree

### Вариант A: независимая работа

Каждый worktree получает свой дом. Переписки, состояния и курьеры не смешиваются.
Это два независимых канала, а не общий.

### Вариант B: общий канал между worktree

Нужен один физический `.house`, а не копия в каждом worktree. Варианты:

- общий coordination-root, который является родителем рабочих каталогов;
- один `.house` в одном worktree и junction/symlink из второго.

Простая копия каталога создаёт два независимых дома и ломает ожидание общего
журнала. На Windows проверь, что оба пути открывают один каталог:

```powershell
(Get-Item C:\work\my-project-a\.house).Target
(Get-Item C:\work\my-project-b\.house).Target
```

## 7. Восстановление после потери сессий

Дом, журнал и рабочие файлы остаются в проекте; sessionId, PID и курьер относятся к
временным окнам. Новые окна нужно зарегистрировать заново.

1. Запусти новые сессии в том же проектном каталоге.
2. Проверь дом командой `/house status`.
3. Выполни `/house setup`, выбери новые активные сессии и назначь роли из
   `house.json`.
4. Запусти `/house start`.
5. Прочитай `.house\переписка.md` и рабочие файлы задачи, восстанови контекст.
6. Отправь тестовый блок в обе стороны и проверь доставку.

Не запускай `init`, если нужно продолжить старую переписку: это может создать новый
конфиг вместо восстановления старого. Старая запись в `sessions.json` не делает
сессию живой.

## 8. Перенос старого дома

Перенос нужен, когда дом переезжает в другой проект или начинается новая переписка.

1. Останови старый курьер:
   `node <путь к House>\src\house.mjs stop --cwd <старый проект>`.
2. Сохрани `переписка.md` и `state.json` как архив.
3. Создай новый дом через `init`.
4. Зарегистрируй новые сессии через `/house setup`.
5. Запусти новый курьер.
6. Старый журнал оставь архивом; не используй старый `state.json` как новый:
   метки `lastSentBy`, `deliveredBy` и `notified` привязаны к старым participantId.
7. Сделай тестовый обмен в обе стороны.
8. Проверь `sessions.json`, `state.json` и `logs\inbox.log`.

Перенос не считается завершённым, пока сообщения видны только в терминале. Приёмка
идёт по файлам и живому обмену.

## 9. Проверка после запуска

```powershell
node <путь к House>\src\house.mjs status --cwd C:\work\my-project --json
Get-Content C:\work\my-project\.house\sessions.json
Get-Content C:\work\my-project\.house\state.json
Get-Content C:\work\my-project\.house\logs\inbox.log -Tail 20
```

Проверяй:

1. В `sessions.json` есть оба участника, новые PID и `processStartedAt`.
2. В `state.json` есть `lastSentBy` и `deliveredBy`.
3. В `logs\inbox.log` появилась строка `delivered`.
4. Автор блока совпадает с заголовком, а не с подписью внутри тела.
5. Ответ пришёл отдельным блоком, а не только строкой доставки.

## 10. Обновление House

```powershell
cd <путь к репозиторию House>
node install.mjs --profile <profile-a> --dry-run
node install.mjs --profile <profile-a>
```

После обновления перезапусти только сессии обновлённых профилей. Дома и переписки
при обновлении профиля не удаляются.

Правки нельзя делать только в `~/.omp/profiles/<profile>/agent`: это потребительский
каталог. Источник истины это `src/` репозитория House.

## 11. Проверка соответствия профиля и источника

```text
node <путь к проекту>\.house\house.mjs verify --cwd <путь к проекту>
```

Команда печатает `OK` или `DIFF` по каждому файлу и возвращает `0` при совпадении,
`2` при расхождении. Она сравнивает профиль с репозиторием по `sourceRoot` из
манифеста.

## 12. Доставка, показ и ответ

`delivered` в `logs\inbox.log` означает «поставлено в очередь окна». Строка пишется
сразу после `sendUserMessage(..., { deliverAs: "steer" })`, до показа. Показ меряется
только наблюдением принимающего окна; ответ это новый блок в `переписка.md`.

| Величина | Чем меряется | Что означает |
|---|---|---|
| Инъекция | `delivered` в `inbox.log` | постановка в очередь, не показ |
| Показ | наблюдение принимающего окна | между какими вызовами встал блок |
| Ответ | новый блок в `переписка.md` | длина хода, а не поломка доставки |

Инъекция идёт с `steer`: блок встаёт между вызовами инструментов текущего хода и ход
не прерывает. Вне стриминга `steer` и `followUp` неотличимы.

После смены `sessionId` (resume) привязка не совпадает с новым id: окно пишет
`unbound`, пока в нём не выполнят `/house setup` заново. После привязки поллер
стартует с нуля и предъявляет хвост переписки. Перезапуск без resume сохраняет
sessionId, метки и не даёт повторной доставки.

### Предел автономной переписки

Инъекция блока в простаивающее окно сама запускает ход, поэтому цепочка «блок,
ответ, блок» может идти без владельца. `courier.autoTurnLimit` (по умолчанию 6)
считает подряд идущие ходы, начатые инъекцией, без слова владельца. После предела
текст инъекции несёт факт петли. Окно всё равно будится и блок показывается: тормоз
мягкий намеренно. Первое слово владельца обнуляет счётчик: работа по его слову
петлёй не считается.

## 13. Что делать при поломке

Сначала файлы, потом поведение:

```powershell
node <путь к House>\src\house.mjs status --cwd C:\work\my-project --json
Get-Content C:\work\my-project\.house\sessions.json
Get-Content C:\work\my-project\.house\state.json
Get-Content C:\work\my-project\.house\logs\courier.log -Tail 20
Get-Content C:\work\my-project\.house\logs\inbox.log -Tail 20
```

| Симптом | Причина | Действие |
|---|---|---|
| `/house` неизвестна | расширение профиля не загрузилось | проверить установку, перезапустить omp |
| Нет новых PID | окно не перезапущено или не записало lease | перезапустить окно, проверить cwd |
| В `inbox.log` только `unbound` | привязка на старый sessionId | `/house setup` заново |
| Нет `inbox.log`, но старые окна получают блоки | работает старый код профиля | обновить профиль, открыть новые окна |
| `delivered` есть, ответа нет | доставка сработала, ответ это отдельный ход | не считать доставку ответом |
| Курьер не работает | `/house start` не выполнялся или процесс упал | `/house start`, затем `/house status` |
| `verify` показывает `DIFF` | профиль разошёлся с источником | переустановить профиль |

## 14. Ограничения

- Всё локально: нет портов, сетевых вызовов, логинов и токенов в `house.json`.
- Аутентификации и шифрования нет: инструмент для одной машины и доверенных окон.
- `auto` даёт headless-агенту право записи, это больше полномочий, чем `notify`.
- При падении окна возможен дубль блока: лучше дубль, чем тишина.
- Дом это файлы проекта. Попадание `.house` в git это осознанное решение команды.
- House не заменяет постановку задач: он доставляет сообщения, а не гарантирует
  выполнение.
